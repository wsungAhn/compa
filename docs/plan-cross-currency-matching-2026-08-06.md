# 실행계획 — 크로스 통화 매칭 (2026-08-06)

> 설계 근거: `design-cross-currency-matching-2026-08-05.md`(4차 실측).
> 이 문서는 **그 이후 바뀐 것을 반영한 실행계획**이다.

## 설계 이후 바뀐 것 — 1층이 이미 해결됐다

원설계의 1단계(브랜드 획득)는 딜 감지용으로 만든 `brand_dictionary`가 그대로 푼다:
89개 브랜드, 한/영 별칭(`토리든`↔`Torriden`), 흔한 단어 오탐 가드. **새로 만들지 않는다.**

## 확정된 결정

| 항목 | 결정 | 근거 |
|---|---|---|
| 실행 시점 | **배치** | 번역이 끼면 수집이 느려진다. 크로스 언어 매칭은 실시간일 이유가 없고 사용자 검색은 이미 DB 조회다 |
| 애매한 매칭 | `needs_review` + **검토 UI** | 쌓기만 하면 없는 것과 같다. 오매칭 비용이 재현율보다 비싸므로 사람이 최종 판단할 자리가 필요하다 |
| 용량 임계 ±8% | **일단 모으고 재산정** | 현 값은 SK-II 한 제품 10건에서 나왔다(적대감사 R1 표본 부족 지적). A단계에서 브랜드 5곳 표기를 모은 뒤 다시 계산 |

## 단계

### A. 용량을 파이프라인에 싣는다 (급소)

실측상 단위 정규화가 없으면 매칭은 **0/10**이다. 그런데 지금 용량 정보가 파이프라인
어디에도 없다 — `ScrapedEvent`에도, `sale_events`에도 없고, Shopify 스크래퍼는
용량이 든 `variant.title`을 **버리고 가격만** 쓴다.

1. `app/core/size.py` — `parse_size_ml(text)`. `2.5 oz → 73.9`, `75ml → 75.0`,
   `1.69 oz → 50.0`. 소수점 보존(실측 버그: `2.5 oz`를 `5oz`로 읽었다), `g ≈ ml`
2. `ScrapedEvent.size_ml` 추가 → Shopify는 variant title, Rakuten·Amazon은 상품명에서
3. `sale_events.size_ml` 컬럼 + Alembic
4. 용량 표기 형식을 수집해 **±8% 임계 재산정** — 표본은 브랜드 5곳이 아니라
   **브랜드당 50건 이상**으로 잡는다(감사 R2). 지금 값은 SK-II 한 제품 10건에서 나왔다

**완료 판정**: SK-II 75ml(JP)와 2.5oz(US)가 같은 용량으로 정규화된다.

### B. 매칭 코어 — 순수 함수

DB·네트워크에 닿지 않는다. 전부 오프라인 테스트.

1. 노이즈 제거: `【公式】【送料無料】【ふるさと納税】正規品 並行輸入品`
2. **포함도** 점수(정본 토큰 ⊆ 리스팅 토큰). 자카드는 정답 쌍을 0.25로 떨어뜨렸고
   포함도로 바꾸니 1.00이었다 — JP 리스팅은 별칭·노이즈로 토큰이 과잉이라 분모가 부푼다
   - **정본 쪽 상표·마케팅 토큰은 분모에서 뺀다**(`PITERA™` `LXP` 등). 실측 2차에서
     US 정본이 `PITERA™ Facial Treatment Essence`였는데 JP 리스팅엔 PITERA가 없어
     정답 쌍의 점수가 깎였다. 스톱워드로 처리하지 않으면 정본이 화려할수록 매칭이
     어려워지는 역전이 생긴다 (적대감사 R2)
3. 용량 대조(A에서 재산정한 임계)
4. **샘플 가드**: `お試し` `トライアル` `sample` `ミニ` `분장` 키워드 + 같은 정본에
   붙은 리스팅들의 ml당 단가 **중앙값 대비 이탈**. 단일 상수(1/3)는 50% 할인 샘플을
   통과시킨다(감사 R1 지적)
   - **단가 이탈은 거부가 아니라 `needs_review`로 보낸다**(감사 R2). 진짜 깊은
     할인(재고 정리 70% off)이 샘플과 같은 신호를 낸다 — 자동 거부하면 가장 값진
     딜을 우리 손으로 숨긴다. 키워드가 함께 걸릴 때만 자동 거부

**완료 판정**: 실측에서 나온 실제 문자열 6종이 테스트로 고정된다
(75ml↔2.5oz 매칭 / 30ml↔73.9ml 거부 / 노이즈 제거 / 샘플 거부 / 단가 이탈 거부 /
브랜드 없는 공홈명).

### C. 번역 계층

#### 선행조사(로컬모델 실측, 2026-08-06)

**① 레포 내 검색**: `app/ai/translator.py`가 이미 있다 — `detect_language`(유니코드
비율로 ja/zh/ko/en 판별), 인메모리 캐시(maxsize 1000, 초과 시 전체 clear), `deep_translator.
GoogleTranslator` 호출, try/except 실패 시 원문 반환까지 C단계가 필요로 하는 골격이
이미 90% 있다. **새로 만들지 않는다 — 엔진만 교체한다.**

**② 외부 — 로컬모델 실측**: 이 Mac에 이미 Ollama가 있지만 pull된 모델은 전부 14~32B
범용 모델뿐이라 번역 전용으로 쓰기엔 무겁다. 조사 결과 `translategemma:4b`(Google,
Gemma 3 기반 전용 번역모델, 2026 출시, [blog.google](https://blog.google/innovation-and-ai/technology/developers-tools/translategemma/),
Apache 2.0)를 채택 — 3.3GB(Q4_K_M), 55개 언어, Ollama로 바로 pull(`ollama pull
translategemma:4b`, 최근 커밋/릴리스 활성). Pull 후 실측 4건(JP 노이즈 포함/제거,
JP 샘플 키워드, KR, ZH):

- 나이브 프롬프트("Translate to English: ...")는 수다스러운 잡담체 출력 → **정형
  프롬프트 필수**(`You are a professional {SRC} to {TGT} translator... Produce only
  the {TGT} translation, without any additional explanations`). `/api/generate`로
  호출하면 0.3~0.7초/문장, 깨끗한 한 줄 출력.
- **함정 1 — 브랜드명 음역 오류**: "토리든"(Torriden) → "Tori Den"으로 오역. 그대로
  두면 `containment_score`가 깨진다(정본 "Torriden" 토큰과 안 겹침). **해법**: 번역
  호출 전에 `app/scrapers/brand_dictionary.py`의 기존 `BRAND_ALIASES`로 원문의 별칭을
  정본 영문 브랜드명으로 먼저 치환한다(신규 사전 아님, 재사용).
- **함정 2 — 샘플 키워드 손실**: "トライアル" → "Trial Size"로 번역됨.
  `app/ai/matching.py`의 `_SAMPLE_KEYWORDS`엔 "sample"만 있고 "trial"이 없다. **해법**:
  `is_sample_listing`은 번역 전 원문에 호출해야 한다 — B단계 `evaluate_match` 설계가
  이미 `listing_name`(원문)에 직접 호출하도록 돼 있으므로 **D단계 배선만 원문 유지하면
  된다**(B단계 코드 변경 불요).

**③ 결론**: `deep-translator`(외부 GoogleTranslator) → 로컬 `translategemma:4b`로
교체. 외부 API 의존이 사라지므로 원 설계문서(`design-cross-currency-matching-
2026-08-05.md`)가 "범위 밖"으로 미뤄둔 **캐시 영속화는 이번에도 미룬다** — 그 항목의
근거였던 "외부 API에 얹힌다"는 전제 자체가 로컬 엔진으로는 성립하지 않는다. 인메모리
캐시의 "1000건 초과 시 전체 clear" 비효율만 이번에 같이 손본다(파일을 만지는 김에
LRU로 — 별도 라운드를 만들 정도는 아니다).

**④ 추론 위치 — 랩탑으로 오프로드(2026-08-06 사용자 지시)**: Mac Studio는 지금 헤비한
로컬모델 벤치테스트가 돌고 있어 자원을 나눠쓰면 안 된다. 랩탑(Windows, `AlienWare-Home`,
LAN `192.168.86.34:11434`)에 이미 Ollama가 LAN 노출돼 있고(`nomic-embed-text` 등 기존
임베더 워크로드가 거기서 돈다) `translategemma:4b`를 새로 pull해 실측 확인 완료 —
웜업 후 0.5~1초/문장으로 Mac Studio 실측(0.3~0.7초)과 큰 차이 없다(첫 호출은 모델
로드로 ~11초, 이후 캐시됨). `settings.ollama_url`(범용, `qwen2.5-coder:32b` 등 무거운
로컬 AI용)과 분리된 **`settings.translation_ollama_url`**로 이 엔드포인트를 가리킨다 —
같은 설정을 공유하면 다른 기능이 랩탑 쪽으로 잘못 라우팅될 위험이 있다.

브랜드 음역 비결정성도 이번에 다시 확인됨: "토리든"이 호출마다 "Tori Den"/"Toryden"으로
다르게 나온다(온도>0로 추정) — ②의 함정 1(브랜드 별칭 사전 치환) 해법이 필수임을
재확인.

카탈로그 2,541건 중 비영문만 대상(`detect_language`가 이미 en을 거른다).

**번역 실패를 감지한다**(감사 R2). 번역이 실패하면 원문이 그대로 돌아오거나 빈 문자열이
되는데, 그러면 포함도가 조용히 0이 되고 우리는 그걸 "매칭 없음"으로 읽는다 — 오늘만
네 번 겪은 조용한 실패와 같은 부류다. 최소 검사: **출력이 입력과 다를 것**, JP/KR
입력이면 **출력에 라틴 문자가 있을 것**. 실패하면 매칭을 시도하지 않고 그 사실을 남긴다.

### D. 배치 매칭 + 검토 UI

1. Celery 태스크: 미매칭 `sale_events`를 US 정본 카탈로그에 붙인다
2. 확신: 자동 연결 / 애매: `needs_review=True`로 보류 / 샘플·단가 이탈: 거부
3. **검토 UI**: `needs_review` 목록 + 승인/거부 버튼. `admin.py`에 이미 있는
   `require_admin` 게이트를 재사용한다
4. 승인된 매칭만 크로스 통화 비교에 노출

**완료 판정**: 라쿠텐 JPY와 공홈 USD가 한 product로 묶여 `comparison?currency=KRW`가
"일본이 N% 싸다"를 계산한다.

## 실패하면 어떻게 아나

- A: 정규화 후에도 JP/US 용량이 안 맞으면 → 표기 형식을 더 모아야 한다
- B: 포함도 임계가 재현율을 죽이면 → 임계를 낮추지 말고 **번역 품질**을 먼저 의심한다
  (오매칭이 재현율보다 비싸다)
- D: `needs_review`가 쌓이기만 하면 → 자동화 비율이 낮은 것이므로 B의 임계·번역을
  재검토. **큐가 길어지는 것 자체가 신호다**
