## 1. Introduction / Overview

제품명을 입력하면 여러 국가·플랫폼의 할인 이력과 **인플루언서 딜 신호**(US-006)를
모아 "지금 살지, 기다릴지"를 추천하는 화장품 가격 비교 서비스. 백엔드(수집·매칭·
예측 파이프라인)가 프론트엔드(단일 화면 SPA)보다 훨씬 앞서 있다는 게 이 PRD의
핵심 전제다 — 이 문서의 절반은 "이미 만든 걸 사용자가 볼 수 있게 하는 것"에
관한 것이다.

## 2. Goals

- 사용자가 "이 가격이 싼가, 다른 데가 싼가, 기다려야 하나"를 한 화면에서 판단할 수
  있게 한다(대부분 이미 됨 — §4).
- 이미 완성된 백엔드 자산(크로스 통화 매칭 검토 큐, 딜 신호 원본, 세일 예측)을
  사용자·운영자가 실제로 접근 가능하게 한다.
- 자가서비스 수익화 경로(구독 결제)를 연다 — 지금은 사전발급 키 방식이라 "구매"가
  불가능하다.
- 소셜 콘텐츠(인플루언서 딜 신호·GRWM)를 가격 비교를 넘어선 발견(discovery) 자산으로
  확장한다 — 딜 신호는 US-006으로 확정, GRWM 조합 추출은 진행 확정이나 데이터소스
  설계는 아직(§10 Open Questions).

## 3. 타깃 사용자 (2026-08-07 정정)

**연령·관심사 기준이지 국적 기준이 아니다.** 1차 고객은 한국이지만, UI/UX가
국가별로 갈라질 이유가 없다 — 국가는 가격 비교의 **입력값**(어느 나라 가격을
비교하는지)이지 사용자 **세그먼트**가 아니다.

- **핵심 타깃**: 성별 무관, **20대 후반~40대**, 스킨케어·화장품에 관심 있는 소비자.
  "직구족"처럼 좁게 규정하지 않는다 — 국내에서만 사는 사람도 "이 가격이 싼가"는
  똑같이 궁금하다.
- 크로스 통화 비교는 이 타깃 안의 **부분집합**(해외구매 관심층)에게 특히 유효한
  기능이지, 별도 세그먼트가 아니다.

  무의미). Amazon 어소시에이트 승인 나면 태그만 채우면 즉시 작동(코드 변경
  불필요) — 별도 확인 필요.

## 5. User Stories (남은 갭 — 우선순위 순)

### US-001: 결제/구독 자가서비스
**Description:** As a 사용자, I want 카드로 직접 구독을 결제 so that 사전발급 키를
누군가에게 요청하지 않고도 프리미엄을 쓸 수 있다.

**Acceptance Criteria:**
- [ ] **Stripe로 시작**(확정, 2026-08-07) — 국내 PG(토스페이먼츠 등)는 나중에
  **병행 추가**(교체 아님, 카드사/지역별 라우팅 또는 체크아웃에서 선택). 지금
  둘 다 붙이지 않는 이유: 웹훅·정산대사·실패케이스가 그대로 두 배가 된다 —
  Working Skeleton First(하나로 시작, 실제 마찰이 확인되면 두 번째를 얹는다)
- [ ] 구독 상태가 DB에 저장(현재 `premium_api_keys` 정적 목록 방식 폐기)
- [ ] `X-Premium-Key` 인증 경로를 구독 상태 조회로 교체(기존 API 계약 유지)
- [ ] 결제 실패/취소/환불 경로 처리
- [ ] **무인 자동구현 금지** — 결제는 전 과정 유인 리뷰(Fable 권고, §8)

### US-002: 크로스 통화 매칭 검토 화면
**Description:** As a 운영자, I want `product_match_candidates`의 pending 항목을
화면에서 승인/거부 so that curl로 API를 직접 안 두드려도 된다.

**Acceptance Criteria:**
- [ ] `/api/admin/product-matches` 목록을 표로 렌더(양쪽 제품명·브랜드·score 표시)
- [ ] 승인/거부 버튼 → 기존 API 그대로 호출(409 처리 포함)
- [ ] `X-Admin-Secret` 인증(기존 방식 재사용, 새 인증 발명 금지)
- [ ] Verify in browser using dev-browser skill

### US-003: 딜 신호 원본 피드
**Description:** As a 사용자, I want Reddit/Slickdeals에서 온 "지금 화제인 딜"을
직접 볼 so that SaleEvent로 흡수되기 전 원본 신호(할인율·출처·시각)를 놓치지 않는다.

**Acceptance Criteria:**
- [ ] 딜 신호 원본을 노출하는 API 신설(현재 없음 — 저장은 되지만 읽는 경로가 없다)
- [ ] 프론트에 피드 화면(리스트, 최신순)
- [ ] 48시간 보존 정책과 UI가 일관(만료된 딜은 안 보임)
- [ ] Verify in browser using dev-browser skill

### US-004: 매칭 커버리지 가시화
**Description:** As a 운영자, I want 전체 카탈로그 중 크로스 통화 매칭이 끝난 비율을
볼 so that 배치 주기(6시간)가 충분한지 판단할 수 있다.

**Acceptance Criteria:**
- [ ] 고아 상품 수 / 전체 상품 수 지표(관리자 화면 또는 API)
- [ ] 매칭 안 된 대표 상품 목록(디버깅용)

### US-005: 프론트엔드 라우팅 도입
**Description:** As a 개발자, I need 최소한의 라우팅(또는 탭 구조) so that 딜피드·
어드민 화면을 단일 컴포넌트 트리에 억지로 끼워넣지 않아도 된다.

**Acceptance Criteria:**
- [ ] **react-router로 확정**(2026-08-07 — 가장 널리 쓰이는 표준, React 19와
  호환성 좋음, 논쟁거리 아니라 바로 결정)
- [ ] 기존 검색→비교 플로우가 회귀 없이 동작
- [ ] 딜피드(US-003)·어드민(US-002)이 각자 경로를 가짐
- [ ] Verify in browser using dev-browser skill

### US-006: 인플루언서 딜 신호 — **보류 (2026-08-09 강등)**

> **v4 보류 사유**: 이 스토리의 전제("기존 소셜 파이프라인의 소스 확장")가 현재
> 사실이 아니다 — 그 파이프라인(instagram/tiktok/facebook/naver 수집기 522줄 +
> extractor/pipeline)은 전 기간 산출 **포스트 0건**(DB 실측: slickdeals 6 +
> reddit 1이 전부)으로, 확장할 "기존"이 아직 작동한 적이 없다. 기능 자체는 필요
> 확정(사용자, v3에서 요청·2026-08-09 재확인) — 버리는 게 아니라 **수집기부터
> 고쳐야 착수 가능**하다는 뜻의 보류. 산출 0 원인 판별은 §12-4. 재개 조건:
> 수집기가 실제 포스트를 물어오는 걸 증명(후보: frankencrawler Instagram 경로 —
> 계정통계 랜딩 실적 있음) + §12-1③ 재시도 루프 수술 완료.
**Description:** As a 사용자, I want 인플루언서가 인스타/틱톡에 올린 할인코드·
할인링크를 다른 딜 신호(Reddit/Slickdeals)와 같은 자리에서 볼 so that 지금
살까 말까 고민 중인 제품에 쓸 수 있는 코드가 있는지 놓치지 않는다.

**2026-08-07 스코프 정정**: 처음엔 "협찬(유료광고) 여부 감지"로 논의됐으나,
**협찬 여부는 무관하다**로 확정(사용자 확인) — 이 앱을 쓰는 사람은 이미 "사겠다/
필요하다"고 마음먹은 상태에서 스마트한 딜을 찾는 것이지, 광고 여부를 판별해주는
서비스가 아니다. 그러면 이건 **신규 기능이 아니라 기존 소셜 파이프라인
(`app/social/`, `app/ai/extractor.py`, `app/ai/pipeline.py`)의 소스 확장** —
Reddit/Slickdeals에서 "할인코드+가격"을 뽑는 것과 동일한 추출 로직을 인플루언서
게시물에 적용하면 된다.

**Acceptance Criteria:**
- [ ] 인스타/틱톡 게시물에서 제품명+할인코드(또는 링크)+가격 추출(기존
  `extractor.py` 패턴 재사용, 새 AI 파이프라인 발명 금지)
- [ ] 추출된 딜이 US-003(딜 신호 피드)에 같은 형식으로 합류
- [ ] 협찬/광고 여부 판별 로직은 만들지 않는다(Non-Goal, §7)
- [ ] 존재하지 않는 코드/만료된 코드를 걸러내는 최소 검증(가능하면)

## 6. Functional Requirements

- FR-1: 구독 결제 연동은 기존 `X-Premium-Key` 게이트를 대체하되, 그 게이트를 쓰는
  기존 엔드포인트(`/api/products/{id}/events` 등)의 응답 계약은 바꾸지 않는다.
- FR-2: 매칭 검토 화면은 `app/api/admin.py`의 기존 3개 엔드포인트만 쓴다 — 새
  어드민 API를 만들지 않는다.
- FR-3: 딜 신호 피드 API는 기존 SaleEvent/SaleWindow 스키마를 바꾸지 않는다(원본
  신호를 노출하는 새 읽기 전용 API만 추가).
- FR-4: 매칭 커버리지 지표는 `product_match_candidates` + `products` 테이블의
  단순 카운트 쿼리로 충분하다 — 새 집계 테이블을 만들지 않는다.
- FR-5: 라우팅 도입은 기존 컴포넌트(`SearchBar`, `PriceComparison` 등)를 재작성하지
  않고 페이지 컨테이너로만 감싼다.
- FR-6: 인플루언서 딜 신호(US-006)는 협찬/광고 여부를 판별하지 않는다 — 할인
  코드·가격 추출만 한다. 판별 로직을 넣으면 스코프 위반이다.

## 7. Non-Goals (범위 밖)

- 한국·중국 소스의 완전한 크로스 통화 매칭(JP만 라이브 검증됨)
- 실시간 환율(정적 테이블 유지)
- 자체 결제 게이트웨이 신규 구축(기존 PG 연동 우선)

기능들은 내가 필요하다고 한 기능일 확률이 높다") — 산출 0인 서브시스템들은
PRD가 요구하는 기능(4개국 비교=§1, 인플루언서 신호=US-006)의 구현체다. 감사가
확정한 것은 **§12-1의 루프 구조가 병들었다는 것**이지 기능이 불필요하다는 게
아니다. 각 항목의 산출 0 원인(차단됨/배선 안 됨/한 번도 실행 안 됨/조용히
고장)을 12-4에서 가르고, 항목별 처분(수리/보류/삭제)은 그 뒤 사용자가 결정한다.
특히 리테일 스크래퍼는 **사용자 검색 시 온디맨드 경로**(`run_collection_slow`)에
물려 있을 수 있어 삭제 판단 전 실사용 배선 확인이 필수다.

### 12-3. 수술 계획 (독립 커밋 체인)

**처분 원칙(사용자 확정 2026-08-09)**: 요구된 기능이 작동하지 않으면 **재작성
대상이지 삭제 대상이 아니다.** 삭제는 "요구된 적 없거나 요구가 철회된 코드"에만
허용되고, 그것도 12-4 전수 검토 뒤 항목별 승인으로만.

1. **Fix 선행** — ①은 수정+회귀주입 검증 완료(미커밋). ②③은 같은 처방:
   실패 시 상태 전이 필수 + 정기 루프에서 LLM 호출 제거(§7 Non-Goal).
2. **태스크 레벨 에러 전파** — 외부 호출 실패를 `succeeded: 0`으로 둔갑시키는
   `except Exception: continue`(56곳 중 태스크/AI 레이어분) 제거, 실패 카운트를
   반환값·로그에 노출. 스크래퍼 내부 삼킴은 기존 스펙이라 유지.
3. **고장 기능 재작성 백로그화** — 12-4에서 원인이 갈린 항목별로 재작성
   태스크를 등재(스크래퍼는 차단 우회 방식까지 명시). 우선순위는 제품 전제
   (4개국 비교) > US-006 순.
4. **재기동 게이트** — 1~2 랜딩 + 크레딧 충전 후, 관찰 지표는 태스크 종료코드가
   아니라 **외부 API 응답코드 분포**로(Verification Before Done).

수술 후 예상: 정기 LLM 호출 0회. 코드량은 재작성 범위가 정해진 뒤 산출.

### 12-4. 산출 0 서브시스템 전수 검토 (2026-08-09, 코드·설정·로그 실측)

**소셜 수집 4종 — "고장"이 아니라 "열쇠가 없다".** 4개 수집기 전부 `collect()`
첫 줄이 자격증명 게이트인데, `.env`의 해당 키가 **전부 빈 값**이다
(`INSTAGRAM_ACCESS_TOKEN`·`TIKTOK_CLIENT_KEY`·`NAVER_CLIENT_ID/SECRET` — backend/
루트 양쪽 확인). 토큰이 없으면 **로그 한 줄 없이 빈 리스트를 반환**하므로 3개월간
"돌고 있지만 0건"으로 보였다 — 코드는 한 번도 진짜 실행된 적이 없다. 처분:
재작성 불요. 필요한 것은 ①자격증명 발급(Instagram Graph API는 Meta 앱,
TikTok Research API는 승인제 — 사용자 액션) 또는 ②frankencrawler 경로로 소스
대체(설계 필요), ③최소 수정: 토큰 부재 시 기동 로그에 명시(조용한 스킵 금지).

**리테일 스크래퍼 — 레지스트리 13종의 실상은 4분류.**
`enabled_scrapers="Sephora,Amazon US,Rakuten,brands"`(config.py:39) 기준:
| 분류 | 플랫폼 | 상태 |
|---|---|---|
| 활성+작동 | Sephora·Amazon US·Rakuten (+공홈 brands) | 08-05 라이브 검증. 산출이 적은 건 온디맨드 검색 호출 자체가 적어서 — 정상 |
| 차단 | 올리브영(firecrawl 스텔스도 실패)·Ulta(JS 셸) | 우회 재설계 필요 |
| 구현됐으나 비활성 | 쿠팡(403 이력)·@cosme·Tmall·小红书 | 비활성 사유 문서화 안 됨 — 검증 후 활성화 판단 |
| 소스 소멸 | 네이버쇼핑 | API 종료 예고 + 쇼핑은 이관 대상에서 제외(scrapers.md) |
처분: **"4개국 비교" 중 KR축이 통째로 죽어 있는 게 진짜 문제**(올영 차단+쿠팡
비활성+네이버 소멸). CN축도 비활성. US/JP만 산다. 삭제가 아니라 KR 가격 소스
재설계(`design-kr-price-source-2026-08-05.md` 이미 착수됨)가 P0 재작성 항목.

**식별자 폐기 실측(2026-08-09) — LLM 매칭은 식별자 설계 공백의 대타였다.**
활성 소스 3종 전부가 안정 식별자를 응답에 실어 보내는데 스크래퍼가 전부 버린다:
Rakuten API `itemCode`(미사용 확인), Amazon PA-API `DetailPageURL`(ASIN이 URL에
포함되나 미추출), Shopify `products.json`의 `id`/`handle`(URL 조립에만 사용).
`Product` 모델엔 외부 식별자 컬럼이 하나도 없다 — 정체성이 4개 언어 이름 컬럼의
퍼지 매칭뿐이고, 그 퍼지함을 LLM이 메우고 있었다. 선행 제품들(Keepa=ASIN,
다나와=EP 피드, Google Shopping=Merchant Feed)은 전부 식별자로 푼 문제다.
**후속(Tier 2, 설계문서+선행조사 필수)**: `platform_product_ids`(product ×
platform × external_id) 매핑 테이블 + 스크래퍼가 식별자 저장 → 같은 플랫폼
재수집은 exact join(볼륨의 대부분), 크로스 플랫폼 최초 연결만 매칭 문제로 남음.
제휴 네트워크 가입(§11) 시 따라오는 구조화 피드(SKU)가 이 테이블의 두 번째
공급원 — 수익화 액션과 같은 열쇠다.

**AI 레이어 — 입력이 없어 놀았을 뿐, 검색 경로에 실배선.** `matcher.
get_or_create_product`는 사용자 검색(`collect_on_demand`, collector.py:309)에
물려 있고 브랜드 후보가 2+일 때만 Claude를 부른다(유인 트리거라 §7 Non-Goal
비위반). 08-08의 382회 폭주는 구 일일수집이 이 경로를 전 상품에 돌린 탓 — 신
스윕 코드가 이미 해소(08-09 실측 0회). extractor는 소셜 입력이 살아나면 필요.
**단 발견된 라이브 결함**: 크레딧 0 상태에서 검색하면 `_ask_claude_for_match`가
400을 삼키고 None을 반환 → 매칭 실패 → **중복 상품이 조용히 생성**된다. 루프
수술(①~③)과 함께 이 퇴화 경로도 명시 처리(카운터·로그) 대상.

### 12-5. LLM 공급 정책 (2026-08-09, 사용자 확정 — 이 절이 정본)

**종량제 API(Anthropic API 키 경로)는 사용하지 않는다.** 서열:
1. **기계 파싱** — 규칙으로 열거 가능하면 무조건 기계(Deterministic First).
   Reddit/Slickdeals 제목, 할인코드 패턴, 식별자 join(12-4)이 전부 여기.
2. **로컬 Ollama** — 기계로 안 되는 잔여(자유 텍스트 추출 등). `USE_LOCAL_AI`
   경로(`ai/local_client.py`)가 이미 있다.
3. **구독 세션** — 로컬로 품질이 안 나오는 예외만, 유인 트리거로 구독 계정을
   빌려서(headless `claude -p` 등). 무인 정기 루프에는 못 들어간다.

집행은 코드 가드가 아니라 **키 부재로 기계적으로 강제**: `.env`의
`ANTHROPIC_API_KEY`를 비웠다(원값은 같은 파일 주석에 보존). 모든 Claude 경로가
키 유무로 게이트되어 있어 키가 비면 전부 비활성 — LLM 준수는 통제가 아니고,
결정적 차단만이 통제다.
