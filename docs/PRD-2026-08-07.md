## 1. Introduction / Overview

제품명을 입력하면 여러 국가·플랫폼의 할인 이력을 모아 "지금 살지, 기다릴지"를
추천하는 화장품 가격 비교 서비스. 백엔드(수집·매칭·예측 파이프라인)가 프론트엔드
(단일 화면 SPA)보다 훨씬 앞서 있다는 게 이 PRD의 핵심 전제다 — 이 문서의 절반은
"이미 만든 걸 사용자가 볼 수 있게 하는 것"에 관한 것이다.

## 2. Goals

- 사용자가 "이 가격이 싼가, 다른 데가 싼가, 기다려야 하나"를 한 화면에서 판단할 수
  있게 한다(대부분 이미 됨 — §4).
- 이미 완성된 백엔드 자산(크로스 통화 매칭 검토 큐, 딜 신호 원본, 세일 예측)을
  사용자·운영자가 실제로 접근 가능하게 한다.
- 자가서비스 수익화 경로(구독 결제)를 연다 — 지금은 사전발급 키 방식이라 "구매"가
  불가능하다.
- 소셜 콘텐츠(인플루언서 하울·GRWM)를 가격 비교를 넘어선 발견(discovery) 자산으로
  확장할 기반을 놓는다(§9 Open Questions — 설계 전).

## 3. 타깃 사용자 (2026-08-07 정정)

**연령·관심사 기준이지 국적 기준이 아니다.** 1차 고객은 한국이지만, UI/UX가
국가별로 갈라질 이유가 없다 — 국가는 가격 비교의 **입력값**(어느 나라 가격을
비교하는지)이지 사용자 **세그먼트**가 아니다.

- **핵심 타깃**: 성별 무관, **20대 후반~40대**, 스킨케어·화장품에 관심 있는 소비자.
  "직구족"처럼 좁게 규정하지 않는다 — 국내에서만 사는 사람도 "이 가격이 싼가"는
  똑같이 궁금하다.
- 크로스 통화 비교는 이 타깃 안의 **부분집합**(해외구매 관심층)에게 특히 유효한
  기능이지, 별도 세그먼트가 아니다.

## 4. 지금 실제로 서비스되는 기능 (라이브, 코드 직접 확인)

- 제품 검색 → 할인 이력 타임라인 + 가격 추이 차트
- "지금 살지/기다릴지" 추천(WaitBuyWidget) — D-day·다음 세일명·예상 할인율까지
  `core/sale_calendar.py:next_sale()`이 계산해 이미 뜬다
- 플랫폼 간 가격 비교, 크로스 통화 포함(`PriceComparison.tsx`가 "OO에서 N% 더
  저렴해요"를 이미 렌더링 — 갭은 UI가 아니라 매칭 커버리지, §7 FR-4)
- Reddit·Slickdeals 딜 신호 수집(48시간 보존 강제)
- 광고 슬롯 + 프리미엄 키 게이팅(구독 결제 없음)
- 피드백 수집 + 관리자 조회, 제휴 링크 변환(Amazon US·쿠팡·Rakuten)

## 5. User Stories (남은 갭 — 우선순위 순)

### US-001: 결제/구독 자가서비스
**Description:** As a 사용자, I want 카드로 직접 구독을 결제 so that 사전발급 키를
누군가에게 요청하지 않고도 프리미엄을 쓸 수 있다.

**Acceptance Criteria:**
- [ ] 결제 수단(Stripe 등) 연동 — 구체 수단은 Open Question(§9)
- [ ] 구독 상태가 DB에 저장(현재 `premium_api_keys` 정적 목록 방식 폐기)
- [ ] `X-Premium-Key` 인증 경로를 구독 상태 조회로 교체(기존 API 계약 유지)
- [ ] 결제 실패/취소/환불 경로 처리
- [ ] **무인 자동구현 금지** — 결제는 전 과정 유인 리뷰(Fable 권고, §8)

### US-002: 크로스 통화 매칭 검토 화면
**Description:** As a 운영자, I want `product_match_candidates`의 pending 항목을
화면에서 승인/거부 so that curl로 API를 직접 안 두드려도 된다.

**Acceptance Criteria:**
- [ ] `/api/admin/product-matches` 목록을 표로 렌더(양쪽 제품명·브랜드·score 표시)
- [ ] 승인/거부 버튼 → 기존 API 그대로 호출(409 처리 포함)
- [ ] `X-Admin-Secret` 인증(기존 방식 재사용, 새 인증 발명 금지)
- [ ] Verify in browser using dev-browser skill

### US-003: 딜 신호 원본 피드
**Description:** As a 사용자, I want Reddit/Slickdeals에서 온 "지금 화제인 딜"을
직접 볼 so that SaleEvent로 흡수되기 전 원본 신호(할인율·출처·시각)를 놓치지 않는다.

**Acceptance Criteria:**
- [ ] 딜 신호 원본을 노출하는 API 신설(현재 없음 — 저장은 되지만 읽는 경로가 없다)
- [ ] 프론트에 피드 화면(리스트, 최신순)
- [ ] 48시간 보존 정책과 UI가 일관(만료된 딜은 안 보임)
- [ ] Verify in browser using dev-browser skill

### US-004: 매칭 커버리지 가시화
**Description:** As a 운영자, I want 전체 카탈로그 중 크로스 통화 매칭이 끝난 비율을
볼 so that 배치 주기(6시간)가 충분한지 판단할 수 있다.

**Acceptance Criteria:**
- [ ] 고아 상품 수 / 전체 상품 수 지표(관리자 화면 또는 API)
- [ ] 매칭 안 된 대표 상품 목록(디버깅용)

### US-005: 프론트엔드 라우팅 도입
**Description:** As a 개발자, I need 최소한의 라우팅(또는 탭 구조) so that 딜피드·
어드민 화면을 단일 컴포넌트 트리에 억지로 끼워넣지 않아도 된다.

**Acceptance Criteria:**
- [ ] 라우팅 라이브러리 도입(react-router 등 — 기존 관례 없음, 신규 결정)
- [ ] 기존 검색→비교 플로우가 회귀 없이 동작
- [ ] 딜피드(US-003)·어드민(US-002)이 각자 경로를 가짐
- [ ] Verify in browser using dev-browser skill

## 6. Functional Requirements

- FR-1: 구독 결제 연동은 기존 `X-Premium-Key` 게이트를 대체하되, 그 게이트를 쓰는
  기존 엔드포인트(`/api/products/{id}/events` 등)의 응답 계약은 바꾸지 않는다.
- FR-2: 매칭 검토 화면은 `app/api/admin.py`의 기존 3개 엔드포인트만 쓴다 — 새
  어드민 API를 만들지 않는다.
- FR-3: 딜 신호 피드 API는 기존 SaleEvent/SaleWindow 스키마를 바꾸지 않는다(원본
  신호를 노출하는 새 읽기 전용 API만 추가).
- FR-4: 매칭 커버리지 지표는 `product_match_candidates` + `products` 테이블의
  단순 카운트 쿼리로 충분하다 — 새 집계 테이블을 만들지 않는다.
- FR-5: 라우팅 도입은 기존 컴포넌트(`SearchBar`, `PriceComparison` 등)를 재작성하지
  않고 페이지 컨테이너로만 감싼다.

## 7. Non-Goals (범위 밖)

- 한국·중국 소스의 완전한 크로스 통화 매칭(JP만 라이브 검증됨)
- 실시간 환율(정적 테이블 유지)
- 자체 결제 게이트웨이 신규 구축(기존 PG 연동 우선)
- 인플루언서 협찬 감지·GRWM 조합 추출의 실제 구현(§9 — 설계 전 단계)

## 8. 개발 워크플로 (Fable 위임 분석 반영, 2026-08-07)

2026-06-23 Threads 워크플로 제안("역할별 AI 분업 + Codex/Claude Opus 반복검토루프")을
검토한 결과: **compa가 이미 이 제안의 80%를 실행 중**(Tier별 AI 라우팅, GLM 적대감사
+ 리뷰어 diff 검증, Working Skeleton First). 새로 오케스트레이션을 만들지 않는다 —
아래 두 가지만 기존 파이프라인에 추가한다.

1. **PRD를 설계문서보다 먼저 쓴다** — 요구사항이 자명한 항목(스키마가 곧 스펙인
   경우)은 생략 가능하지만, "무엇을 만들 것인가" 자체가 열려 있는 항목(US-002,
   US-003처럼 UI 형태가 정해지지 않은 것)은 `prd` 스킬로 먼저 확정한다.
2. **태스크를 쪼갤 때 항목마다 "완료 판정 명령"을 명시한다**(테스트/스크린샷 등
   기계적으로 pass/fail이 갈리는 명령). 구현자(GLM) 신뢰도가 낮다는 게 D단계에서
   실측됐으므로(중복 태스크 생성, 프로덕션 버그, 테스트 인프라 연쇄 파괴 — 전부
   Claude가 직접 디버깅해서 고침), 판정 명령이 명확하면 리뷰 비용이 "명령 실행"으로
   줄어든다.

**무인 반복 실행(Ralph 스타일) 범위**:
| 백로그 항목 | 무인 루프 | 이유 |
|---|---|---|
| US-002 어드민 UI, US-005 라우팅 | 허용 | API 기존, 기계적 검증(테스트+스크린샷) 가능, 실패해도 무해 |
| US-003 딜피드 | 부분(파이프라인만) | 스크래핑 판단(rate limit 대응)은 유인 필요 |
| US-001 결제 | **금지** | 비가역 외부 부작용, 돈 경로 — 전 과정 유인 리뷰 |

실패 시 왕복 대신 **리뷰어(Claude)가 직접 수정**한다(GLM 왕복 비용이 직접수정보다
컸다는 게 D단계에서 실증됨).

## 9. Success Metrics

- 검색 → 비교 화면 도달률
- WaitBuyWidget 클릭률
- 매칭 커버리지(US-004로 가시화된 뒤 측정 가능)
- 프리미엄 전환율(US-001 이후 측정 가능)
- 어드민 화면 도입 후 검토 큐 처리 시간(현재: curl 수동 운영 기준선 없음 — 도입 후
  측정 시작)

## 10. Open Questions

- **결제 수단**: Stripe인가 국내 PG(토스페이먼츠 등)인가 — 해외 이용자 비중에 따라
  갈림. 결정 필요.
- **인플루언서 협찬 신호**(2026-08-07 제안): 특정 뷰티 인플루언서가 돈을 받고
  제품을 광고하는 걸 "개인 단위 실시간 이벤트"로 감지해 노출하자는 아이디어.
  설계 전 — 협찬 여부를 텍스트/영상에서 어떻게 판별할지(고지 문구 감지? 계약 정보
  없이는 불가능할 수도), 법적/윤리적 문제(허위 협찬 표시 탐지가 오히려 민감할 수
  있음)부터 조사 필요.
- **GRWM 코스메틱 조합 추출**(2026-08-07 제안): "하울"이 아니라 "Get Ready With Me"
  영상에서 인플루언서의 실제 제품 조합(루틴)을 추출해 발견 콘텐츠로 노출하자는
  아이디어. 가격비교와는 다른 축(제품 발견/영감)이라 별도 PRD 필요 — 데이터 소스
  (영상 자막? 설명란? 직접 시청 후 추출?), 저작권/사용 범위부터 확인해야 한다.
- **매칭 배치 주기**: US-004로 커버리지를 실측한 뒤 6시간이 충분한지 재판단.
